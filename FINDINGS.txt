2. ORDER_VS_ AND MATCHING ORDERS
================================================================================

Structure (line 21, 26):
   std::vector<std::vector<uint>> order_vs_;  // Size: [query_.NumEdges()][query_.NumVertices()]

Generation (GenerateMatchingOrder, line 120-253):

   Phase 1 - Global order (lines 123-169):
   • order_vs_[0] = global optimal matching order
   • Starts with highest-degree vertex
   • Expands by maximum connectivity heuristic
   • Used for InitialMatching()
   
   Phase 2 - Incremental orders (lines 172-222):
   • For each query edge i:
     - order_vs_[i][0..1] = the two vertices of edge i
     - order_vs_[i][2..N] = remaining vertices ordered by connectivity
   • Total orders = query_.NumEdges()
   
   Example (8-vertex tree):
   order_vs_[0] = [v_highest_degree, ..., v_lowest_degree]  // global
   order_vs_[1] = [v_edge1_start, v_edge1_end, ..., others]  // incremental
   order_vs_[2] = [v_edge2_start, v_edge2_end, ..., others]  // incremental
   ... (8 total matching orders)

Matching Orders:
   • Global order (order_vs_[0]): Used once in InitialMatching()
   • Edge-specific orders (order_vs_[1..NumEdges-1]): 
     Used when AddEdge/RemoveEdge triggers that edge
   • Why multiple orders? Optimization: each edge update can use
     the optimal order starting from that edge's vertices

================================================================================

A. MAIN PARALLEL LOOP (Line 1339):

   for(size_t t_1 = 0; t_1 < vertex_vector.size(); t_1++)

   • Iterates over vertex_vector entries
   • Each thread calls ProcessNeighbor() which recurses

   Line 1574: #pragma omp for schedule(dynamic, 1)

   Line 1586: #pragma omp atomic
   └─ Atomic increment of shared num_results
   
   Line 1588: #pragma omp barrier
   └─ Wait for all threads before return
   
   Usage (Line 3173):
   Inside PersistentParallelUpdate's outer #pragma omp parallel
   calls Parallel_FindMatches2_inner() to reuse thread team

7. THE 120K+ MYSTERY - BEST EXPLANATION
================================================================================

Given data:
   • 8-vertex query: ~120K calls of PFM2
   • 9-vertex query: ~177K calls of PFM2

Analysis:
   If direct AddEdge calls account for only ~800-1600 calls,
   where do the remaining 118K-175K come from?

Option 1: PROFILER COUNTS RECURSIVE CALLS
   The profiler might count:
   - PFM2 entry (1 call) + all recursive FindMatches_local calls = many calls
   - Each ProcessNeighbor invokes FindMatches_local (depth+1 recursive)
   - Each FindMatches_local can call itself many times
   - Total = exponential growth relative to vertex_vector entries
   
   For 8-vertex query with branching factor ~3-5 at each depth:
   - Depth 2: ~100 vertices in vertex_vector
   - Depth 3: each spawns ~3-5 recursive calls
   - Depth 4+: factorial growth
   - Could easily reach 100K+ total recursive invocations

Option 2: DIFFERENT DATASET
   The 120K-177K might be for a different graph size or density
   (not the toy 8-9 vertex examples used for testing)

Option 3: INTERNAL LOOP COUNTING
   Profiler might count inner for-loop iterations, not just function calls
   Each PFM2 processes u_min_nbrs (thousands of candidates)
   Could accumulate to 120K if counting all candidate iterations

RECOMMENDATION:
   Need to instrument code with timing/counting to determine exactly
   what triggers the 120K calls - direct PFM2 entry points or recursion
