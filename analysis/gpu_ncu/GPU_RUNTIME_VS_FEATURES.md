# GPU BFS runtime vs query-graph features (workload characterization)

> What makes a query "heavy" for the GPU BFS engine? Analysis of **341 random
> 8-vertex query graphs** run on LiveJournal (4.85M V, 38.6M E) with `gpu_bfs`.
> Data: `analysis_8v.json` · Plot: `gpu_features_8v.png` · Scripts:
> `analyze_features.py`, `plot_features.py` (run with `python3.11`).
>
> Queries generated by `scripts/gen_random_queries.py` (Prüfer tree + random
> edges, guaranteed connected), edge counts 7–23, vertex labels 0–29.

---

## TL;DR

**GPU runtime is almost entirely a function of the final match count
(Pearson r = +0.92).** Structural features (edges, degree, cycles, triangles)
only matter *because* they control the match count: **sparser query ⇒ weaker
joinability pruning ⇒ match explosion ⇒ slower GPU.** The slowest 8v query is a
**7-edge tree with 2.46 billion matches at 1.72 s**; the densest 23-edge graphs
finish in ~0.84 s. Note that even the heaviest 8v query is only 1.7 s on the
GPU — **8v is structurally too shallow to stress the GPU** (see ceiling below).

---

## Correlation of GPU time with each feature (n=341)

| feature | Pearson r | reading |
|---|---:|---|
| **# matches** | **+0.92** | dominant — GPU time ≈ f(matches) |
| # edges | −0.23 | weak: more edges → faster |
| max vertex degree | −0.24 | weak: higher degree → faster |
| # independent cycles | −0.23 | weak: more cycles → faster |
| # triangles | −0.16 | weak |
| degree variance | −0.05 | none |
| # distinct labels | +0.04 | none |

All structural features are **weakly negative** — denser/more-constrained queries
run faster. None rivals the match count.

## Tree vs cyclic

| query type | n | GPU median | GPU max |
|---|---:|---:|---:|
| **tree (7 edges, acyclic)** | 18 | 895 ms | **1720 ms** |
| has cycle (8–23 edges) | 323 | 841 ms | 976 ms |

Trees are the only ones that go meaningfully above the ~850 ms floor.

## GPU time by edge count (the trend)

```
 7 edges (tree): median 895ms  max 1720ms   ← heavy
 8 edges       : median 867ms  max  929ms
 9 edges       : median 842ms  max  868ms
10–23 edges    : median ~840ms max ~850–980ms  ← flat at the floor
```

Past 8 edges the GPU time flattens at its fixed floor (~520–850 ms: build CSR +
buffer alloc + a shallow search). Only the sparsest (7-edge tree) queries break
out, and only to ~1.7 s.

---

## The causal chain (why sparse = heavy)

```
sparse / tree query (few edges)
   → few joinability constraints during search
   → candidates barely pruned at each depth
   → match count explodes (10^8–10^9)
   → GPU spends its time enumerating/counting matches  → slow

dense / cyclic query (many edges)
   → many joinability constraints
   → candidates pruned hard (lower_bound fails early)
   → few matches
   → GPU finishes near its fixed-cost floor  → fast
```

The match-count plot (`gpu_features_8v.png`, panel ⑤) shows this directly: on a
log y-axis, the **7-edge trees (red) sit at the top** (10^8–10^9 matches), and
match count drops steeply as edges increase.

---

## The 8v ceiling — and why it matters

Across **341** random 8v queries the GPU **never exceeded 1.72 s**. We could not
synthesize an 8v query that takes the GPU > 10 s (the threshold we used for
"heavy"). This is itself a result:

- **8v search trees are too shallow** to build the giant intermediate frontiers
  that make the GPU slow. The depth-(Q-1) layer simply isn't large enough.
- Conversely it shows GPU strength: 8v queries that take **CPU single-thread
  minutes** (e.g. the 2.46-billion-match tree) are **~2 s on the GPU**.
- To stress the GPU you need **more query vertices** (deeper trees → bigger
  middle layers). Real LJ **9v Q_1 is 22 s** on the GPU; the heavy regime lives
  at 9v–11v, not 8v.

### Practical guidance for generating GPU-heavy benchmarks
- Want heavy → **generate sparse trees** (edges ≈ n−1), not dense graphs.
- 8v tops out at ~1.7 s regardless; use **9v / 10v / 11v** for > 10 s cases.
- Match count is the single best a-priori predictor of GPU cost; if you can
  estimate it (or proxy it via edge sparsity), you can predict heaviness.

---

## Caveats / not yet measured

- These features are **static** (read from the query file). The kernel-internal
  signals — per-depth `partial_match` counts (the real "candidate explosion"),
  whether the buffer overflows/flushes — were **not** captured here (the screen
  run didn't keep `[BFS] Depth d→d+1` logs). Those would likely correlate even
  more tightly with GPU time than the final match count, since they include the
  intermediate blow-up, not just the terminal count.
- Single data graph (LiveJournal) and single stream (2k inserts). "Heaviness"
  is relative to the data graph; a query heavy on LJ may be light on Amazon.
