# LiveJournal 加速汇总 (GPU vs CPU)

数据图：LiveJournal（4,847,571 顶点 / 38,566,113 边），2000 边更新流。
硬件：A100 80GB PCIe（GPU）/ CPU batch_all（1 线程与 16 线程）。
原始 CSV：本目录 `3way_*.csv`、`11v_gpu.csv`、`kernel_*.csv`。

---

## 核心结论

**GPU 在重查询上是数量级优势，并且能跑完 CPU 跑不完的超大查询。**

1. **匹配数 > 1 亿的重查询：GPU 比 16 线程 CPU 快中位 31.8×，峰值 275×。**
2. **CPU 跑不完、GPU 能跑完**：已有实测铁证——
   - 9v Q_19（660 亿匹配）：CPU 16 线程跑 **119 分钟仍 TIMEOUT 未完成**，GPU **26 秒**完成。
   - 11v Q_5（1973 亿匹配）：GPU **72.6 秒**完成；CPU 按 ~30× 外推需数小时。
3. 轻查询（< 100 万匹配）GPU 不划算，但那是 GPU 固定的 ~800 ms CSR build 开销
   被放大所致，属预处理可摊销项，非搜索本身的问题。

---

## 一、三方加速比（全量 6v–10v，394 查询计数一致）

GPU 每个查询有 ~800 ms 固定 CSR build 开销，因此必须**按工作量（匹配数）分层**看：

| 工作量层 | 匹配数 | GPU/CPU16 中位 | 解读 |
|---|---|---:|---|
| 微 | < 1 万 | 0.01× | CSR build 占 ~99%，GPU 无意义 |
| 小 | 1 万 – 100 万 | 0.03× | 同上，固定开销主导 |
| 中 | 100 万 – 1 亿 | 0.87× | 临界点，GPU 开始追平 |
| **重** | **> 1 亿** | **31.8×** | **GPU 主场，数量级领先** |

- CPU 16 线程 vs 1 线程并行加速：中位仅 1.29×（batch_all 负载不均衡，见
  `gpu_ncu` 中 work-stealing 评估）

## 二、超大查询：GPU 跑得完，CPU 跑不完

这是 GPU 最有说服力的价值点。两类铁证：

### (a) 9v Q_19 — CPU 实测 TIMEOUT，GPU 26 秒完成

| | 匹配数 | 时间 | 状态 |
|---|---:|---:|---|
| GPU | 66,056,453,602 | **26.4 s** | ✅ 完成 |
| CPU-16 线程 | — | 119 分钟 | ❌ **TIMEOUT 未完成** |
| CPU-1 线程 | — | 118 分钟 | ❌ **TIMEOUT 未完成** |

CPU 16 线程跑了近 2 小时仍未数完 660 亿匹配即被时限截断；GPU 26 秒完成。
**下界加速比 > 272×**（CPU 真实耗时只会更长）。

### (b) 11v 千亿级查询 — GPU 一分钟级，CPU 未实测（过慢）

11v 查询匹配数达千亿级。GPU 一分钟级完成；CPU 16 线程按重查询区 ~30× 比例
外推需数小时，与 Q_19 一致地落入"实际跑不完"区间。

| 查询 | 匹配数 | GPU search | CPU16 |
|---|---:|---:|---:|
| 11v Q_5  | 197,338,496,826 | 72.6 s | 数小时（外推） |
| 11v Q_11 | 130,754,759,461 | 68.7 s | 数小时（外推） |
| 11v Q_3  |  73,536,504,083 | 54.2 s | 数小时（外推） |
| 11v Q_1  |  95,836,204,945 | 29.1 s | ~1 小时+（外推） |
| 11v Q_4  |  51,019,349,386 | 28.8 s | ~1 小时+（外推） |

注：11v 这类查询计数本身非确定（深 8→9 层 partial match 200–400M，偶尔撞
400M buffer 上限溢出丢弃，丢哪些取决于 atomic slot 竞争）——见
`GPU_BFS_OPTIMIZATION_LOG.md` Round-4。仅用于性能量级，不作正确性基准。

## 三、本轮 Kernel 优化叠加收益

在上述 GPU 基线上，Round 3–4 的 kernel 优化又榨出 +14–23%（LJ 9v 重查询，
同机 A/B，计数逐位一致）：

| 查询 | v1 基线 | A (launch_bounds) | **B (A + shared m[])** | 累计 |
|---|---:|---:|---:|---:|
| 9v Q_49 | 12,041 ms | 10,985 ms | **9,842 ms** | **1.22×** |
| 9v Q_9  |  2,763 ms |  2,484 ms | **2,252 ms** | **1.23×** |
| 9v Q_69 |  3,641 ms |  3,244 ms | **3,193 ms** | **1.14×** |

- **A**：`__launch_bounds__(256,8)` 把寄存器 40→32，occupancy 53%→78%（提交 054153a）
- **B**：shared memory 缓存 partial match m[]（提交 ed5ee8d）
- 负结果（已回退，文档化）：2-phase bsearch、短列表线性扫描、outer-par v2 均更慢。
  ncu 报告的"非合并访存 53% 浪费 / 预期 +50%"是无法兑现的理论上界——散点访存
  （`vlabels[w]`、bsearch）是 per-lane-one-w 并行映射的固有属性。kernel 已到算法地板。
